# git_service

Git リポジトリが持つ情報と操作を、共通インターフェースから利用するためのサービス。

**Git Repository as a Service** をコンセプトに、リポジトリを「取得・設定・起動できる単位」として扱います。

## 目指すこと

リポジトリごとに異なるファイル配置や利用手順を、宣言されたインターフェースを通じて利用できるようにします。

- **発見する**: 公開されている情報・操作と、必要な入力を取得する。
- **取得する**: OpenAPI スキーマやサービスカタログなど、Git 上の成果物を取得する。
- **設定する**: 環境ごとの設定値やシークレット参照を管理ツール側で保持し、実行時に渡す。
- **実行する**: 既存のスクリプトや Docker Compose を利用して、build・up・down・status などの操作を呼び出す。

## 最初の対象

最初は、名前付きクエリによるファイル取得を対象とします。例えば `get_openapi` は、指定したリポジトリと Git ref に格納された OpenAPI スキーマを、そのまま返します。

```text
query(repository, "get_openapi", ref="main")
→ リポジトリ内の OpenAPI スキーマ
```

情報取得だけのリポジトリには、実行環境を要求しません。ブランチ・タグ・コミット SHA を指定して取得し、取得元のコミットを追跡できる設計を目指します。

## 公開契約のイメージ

リポジトリは、公開する情報や操作と、その入力・出力を宣言します。以下は設計例であり、確定した仕様ではありません。

```yaml
version: 1
queries:
  get_openapi:
    description: OpenAPI スキーマを取得する
    file: api/openapi.yaml
    content_type: application/yaml
```

ファイル取得は直接読み出す方式を基本とし、必要に応じて許可された読み取り操作や制限された処理へ拡張します。シェル実行を提供する場合は Alpine を既定候補とし、Git ホスト側での取得・処理も検討します。

## 設定と操作の管理

リポジトリには必要な入力の契約と実行方法を置き、環境ごとの値は管理ツール側に置きます。手作業で `.env` を準備する手順を共通化し、必要に応じて実行時に設定を注入します。

```text
up(repository, ref="v1.0.0", environment="dev")
status(instance)
down(instance)
```

起動操作には、実行先とインスタンスの識別、ログ、状態、停止処理の管理が必要です。単発のクエリと、継続して稼働するサービスの操作を区別します。

## 将来の方向性

複数のリポジトリを同じ環境で動かす際の配置調整を扱うことも検討します。

- 外部ポートや URL の割り当てによる衝突回避。
- インスタンスごとのネットワーク・保存先・設定の管理。
- リポジトリが要求するサービスと、実行環境の資源を結び付けるデプロイ層。
- 指定したバージョンと設定でサービスが稼働する状態の維持。

まずは小さな公開契約とファイル取得から始め、操作実行、単一ホストでの配置調整へ段階的に広げます。

## 位置づけ

Backstage や Port のカタログ・操作機能、Dokploy のデプロイ管理、Dagger の関数公開・実行とは機能が重なります。

git_service が目指すのは、既存のファイルやコマンドに薄い宣言を添え、CLI・管理画面・CI・AI エージェントなどが同じ契約を利用できることです。既存ツールを実行基盤や利用側として接続することも想定します。
